# Decisions

Accepted limits, and rules a review doesn't raise again unless something has changed since, such as a bug report or a new feature that depends on them. A pull request that changes one of these says so, gives the reason and updates this page.

The larger decisions are ADRs in `docs/adr/`: Postgres only (0001), customers bring their own Provider (0002), ports provided per request (0003), API routes under `/api` (0004), and Better Auth per request on the `SqlClient` (0005), IDs in the TypeID format (0006), tenant endpoints that name the Organization in the path (0007), long collections paged by ID (0008), secrets sealed under versioned keys bound to their row (0009), outbound connections going to the address the guard checked (0010), the install set up once with settings only its instance admin can reach (0011), a page reading only the search its route decodes (0012), every dashboard icon coming from one module (0013), queued work acting in the Organization its message names (0014), use cases sending through a Provider Connection with one function (0015), links in emails carrying tokens signed with keys derived from `ENCRYPTION_KEYS` (0016), and a scheduled Campaign starting from a delayed queue message (0017). The overall design is in `docs/architecture.md`, and the security controls are in `docs/security.md`. The entries below came out of the planning on 2026-11-21 unless an issue is named.

## Consent and sending

- A Campaign goes only to Contacts with a subscribed Subscription to a targeted List. It leaves out anyone on an excluded List, with an Opt-out, or with a Suppressed address. Each Contact gets it once.
- "Unsubscribe", both the link and the one-click header, unsubscribes the Contact from every List the Campaign targeted, not just one.
- "Stop all marketing email", on the unsubscribe page, records an Opt-out. Only the Contact can lift it, through the preference center (#13) or, later, a form (#30). An import or the API never can.
- An import never subscribes again a Contact who unsubscribed or has an Opt-out.
- A Transactional Message ignores Subscriptions and Opt-outs but respects Suppressions from bounces and complaints.
- A hard bounce or a complaint suppresses the address at once. Soft bounces suppress it after 3 within 7 days.
- A Suppression blocks one address in one Organization, compared without regard to case, whether or not a Contact has it; a Campaign leaves out any Contact whose address is Suppressed, and so does the check before each email. Its reason is `hard-bounce`, `complaint` or `manual`. A member can add up to 250 addresses in one request (250 of the longest address fit in the 64 KiB request body); one already Suppressed keeps its Suppression and reason, and the answer counts it apart. A member can remove only a `manual` one (`SuppressionNotRemovable`, 409), so a bounce or complaint can't be undone by hand (#14).
- A CSV of Suppressions is read in the dashboard, not uploaded: the browser finds the address column (the one headed email, e-mail or address, or else the first with an address in it, which the member can change), skips rows that aren't addresses, and sends the addresses 250 to a request, one after another. Files are capped at 10 MB, and the file isn't streamed, so the server never sees it. If a request fails, the ones before it stay, and the rest can be sent again; an address already Suppressed is counted, not added twice. The Contact import (#28) is a different job, run in the background on the server (#14).
- A Campaign holds its own copy of its content. Editing the Template later never changes it.
- A Sending Domain that fails DKIM or has no DMARC record blocks a send. SPF alignment problems and `p=none` only warn.
- Every Campaign message has `List-Unsubscribe` and `List-Unsubscribe-Post`, a plain-text part and the Organization's postal address.
- Double opt-in is on by default for hosted signup forms, and an owner can turn it off for a List.
- Sending a Campaign fixes who it goes to in one query, in the same transaction that moves it to `sending`, and queues one message per 100 of them; a send with nobody subscribed is refused (`NoSubscribedContacts`) and leaves a draft (#10).
- A Campaign goes to one or more Lists and can leave out others, up to 20 of each, so a draft with every field at its longest still fits in the 64 KiB request body beside 60 KiB of HTML (25 of each was 15 bytes over); a List can't be in both. A left-out List leaves out anyone with a Subscription to it, whatever its status: someone who unsubscribed from Customers is still a customer. Who it goes to is one SQL query in the repository, which the count shown before sending, the snapshot when it starts sending and the check before each email all use, so they can't disagree. The recipient count is asked for by Lists, not by Campaign, so the form can show it while a member chooses (#15).
- A member schedules a draft for a date and time in a time zone they choose (an IANA name such as `Europe/London`), to the minute. A time the clocks skip when daylight saving starts is moved later by the skip; a time they show twice when it ends is the first. A time that has passed is refused (`ScheduleInPast`, 422). Scheduling is checked as sending now is, so a missing Provider Connection or postal address, or no one to send to, is refused at once. A scheduled Campaign can be moved to another time but not changed or sent now; cancelling its schedule makes it a draft again. One that started sending can't be scheduled or cancelled (`CampaignNotDraft`) (#16).
- A scheduled Campaign starts from a queue message delayed until its time: a pg-boss job with `startAfter` on Node, an outbox row the every-minute Cron Trigger forwards once due on Workers, so it can start a minute late there, and later still behind batches already in the Cloudflare Queue. The message names the time, and the Campaign starts only if it's still scheduled for it, so a cancelled or moved schedule's message does nothing. If its Provider Connection was deleted or no one would get it, it becomes a draft again with `schedule.missed` saying why, kept until it's scheduled again, sent, or its schedule is cleared. If its start fails for another reason, such as Postgres being down, through every retry, it stays `scheduled` at a past time until a member cancels or moves it, as a dropped batch leaves a Campaign `sending` (ADR 0017, #16).
- A batch checks again, just before each email, that its recipient is still subscribed to one of the Campaign's Lists, has no Opt-out and isn't Suppressed, since a batch can take minutes. It doesn't check the left-out Lists again: they were applied when it started sending, and the failure it records says the Contact left (#15). That's read in the statement that claims the recipient, next to the email's own SMTP connection. An unsubscribe, Opt-out or Suppression saved before that check stops the email. One saved while that one email is being handed to the Provider, between the check and the Provider accepting it, doesn't; closing that window would mean holding a lock through the SMTP send. One who isn't is recorded `failed`, saying they left before it was sent, so the Campaign still finishes (#12).
- A Campaign's HTML is at most 60 KiB as a JSON string in UTF-8 (`campaignHtmlBytes`), because the API refuses request bodies over 64 KiB; a character count would let non-ASCII text or many quotes pass and then be refused (#10).
- Every Campaign email has its own unsubscribe link, signed for that Contact and Campaign: in `List-Unsubscribe` with `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, and as a line at the foot of the HTML. There's no `mailto:` unsubscribe until the app can receive email (#21) (#12).
- Opening an unsubscribe link changes nothing: the page asks first, so a mail scanner that opens links unsubscribes nobody. A mail app's one-click post unsubscribes at once. The page then offers "Stop all marketing email", which records an Opt-out (`contacts.opted_out_at`); a Campaign's recipients leave out anyone with one (#12).
- Unsubscribe links don't expire, and their token is in the query string, not the path, because the router caps path parameters at 100 characters (#12).
- The public pages use Kumo components wherever Kumo has one, rendered with React on the server. They're `.ts` files using `createElement`, since the Node server can't read JSX, and they link the dashboard's stylesheet as `/public-pages.css`. Their body text is 16px (`--text-lg`), not Kumo's 14px, because a recipient reads the page once, usually on a phone (#12).
- A Campaign email's plain-text part is made from its HTML as each batch is sent, with `html-to-text`: a link's address follows its words in brackets, and an image is its alt text, so spacer and tracking images leave nothing. Each table row and cell is a block of its own, since most email layouts are tables. A Roman-numeral list is bulleted, because the library numbers one only up to 3,999 and throws past it, which would fail the batch on every retry. Anything hidden with `display: none`, such as a preview line, is left out. Text nested more than 100 elements deep is left out, because reading deeper would overflow the stack and fail the batch. It isn't stored, and a member can't edit it (#13).
- Every Campaign email, HTML and plain text, ends with its unsubscribe and preferences links and then the Organization's name and postal address on one line, the address's lines joined by commas (`withFooterHtml`, `withFooterText` in `domain`, which the dashboard's preview uses too). The address is escaped in the HTML. Each batch reads the address as it is then, so an edit during a send reaches the later batches. A Campaign already sending when the address became required is the one exception, below (#13).
- The preferences page (`/preferences?token=`) lists only the Lists the Contact has a Subscription to, whatever its status, never the Organization's other Lists, so a recipient never sees an internal List's name or joins one. Each List has its own Subscribe or Unsubscribe button that posts at once and comes back to the page, saying what changed, so it works without JavaScript; Kumo's `Switch` and `Checkbox` can't change or submit without it. Its token carries the Organization and Contact, under its own purpose, and doesn't expire, as an unsubscribe link's doesn't (#13).
- An Opt-out leaves each Subscription as it was. So while one is in place, the preferences page shows every List as off, and subscribing to one List lifts the Opt-out and unsubscribes the Contact from every other List, in one statement: they get only what they chose. A pending Subscription subscribed from the page becomes subscribed, since the link proves the address is theirs (#13).
- A Campaign can't be sent until its Organization has a postal address (`PostalAddressRequired`, 409), checked in the transaction that starts the send, once the Campaign is found to be a draft with a Provider Connection and before its recipients are fixed; a draft's page names the missing address before "no one subscribed" in the same order. An address can be changed but never removed. Any member can set it until roles arrive (#34). The one exception is a Campaign already sending when this ships: its remaining batches go out without the address line, rather than stopping mid-send until someone adds one (#13).
- A Contact the Provider refuses for good is recorded as `failed` with the Provider's words and isn't tried again; the others still get it. When the server itself fails for good (TLS, sign-in, blocked, no such host, or a connection lost or timed out partway), the rest of that batch is recorded with the same failure without trying them, so one dead server can't hold the queue for a minute per Contact. A Campaign is `sent` once none of its recipients are still queued or being sent to (#10).
- An email the Provider puts off (`SendDeferred`) is tried again on the batch's next delivery, so it waits out the queue's backoff: an SMTP 4xx reply, such as a busy mailbox or greylisting, or a connection that never opened (refused, unreachable, no greeting, a failed host lookup). When the server can't be connected to, the rest of the batch waits too, untried. Only failures that show the server never took the email are tried again: a connection lost or timed out after the message was sent might have been taken, and trying again could send it twice. On the batch's last delivery, the one after `QUEUE_RETRIES` retries, as the runtime counts them (pg-boss's `retryCount`, Cloudflare's `attempts`), a put-off email is recorded `failed`, and the rest of the batch with it when the server can't be connected to, since the queue then drops the batch and nothing else would send or record them. A delivery that put anyone off fails with `BatchDeferred`, so the queue delivers it again (#17).
- A member can pause a sending Campaign, resume a paused one and cancel either (`CampaignNotSending`, 409, for any other). Each batch checks the Campaign is still sending in the statement that claims each recipient, so a pause or cancel stops it before its next email; one already being handed to the Provider still goes. Pause leaves the rest queued, and the batch ends without asking the queue to deliver it again. Resume queues one message per batch with anyone still queued or claimed, in the transaction that makes it `sending`, so a batch a pause interrupted, or one the queue dropped, is sent. Cancel is final: the rest stay unsent and are counted as neither sent nor failed. A paused Campaign whose last email was being handed over when it paused becomes `sent`, and one whose every email was recorded can't be paused or cancelled: it's marked `sent` and refused. Pausing, resuming or cancelling a Campaign already in that state answers with it, so two members clicking at once aren't refused (#17).
- A Campaign email goes to each recipient at most once. A batch claims each recipient before sending and records them as soon as the Provider answers. One claimed more than two minutes ago and never recorded is recorded `failed`, saying it may or may not have reached them, and isn't sent again. The maintainer chose at most once over at least once: no one gets a second copy, and a rare in-flight email is counted failed though it may have arrived (ADR 0014, #17).
- A batch whose work fails, such as while Postgres is briefly unreachable, is delivered again up to 5 times on both runtimes, so about 15 minutes of outage doesn't leave a Campaign `sending`. On Cloudflare the waits are exactly 30 seconds, then twice as long each time (`queueRetryDelaySeconds`). On Node, pg-boss adds jitter: each wait falls between that and twice it, at most 8 minutes, so the retries span 15 to 23 minutes. After the last retry the batch is dropped (#139), and the Campaign stays `sending` until a member pauses and resumes it, which queues again every batch with anyone left, or cancels it. Nothing does that by itself: the maintainer chose resume as the way out over a sweep that queues stalled batches again on a timer (#17).
- Deleting a Provider Connection leaves its Campaigns without one: a draft can't be sent until another is chosen, and a Campaign still sending records the Contacts it hadn't reached as `failed` (#10).
- On Workers, a send's queue messages go into the `queue_outbox` table in its transaction and are forwarded to Cloudflare Queues when the request ends, and every minute by a Cron Trigger for any left behind. One consumer runs at a time, as pg-boss works on Node, and takes one batch per invocation, one email at a time, so a batch has the 15-minute limit to itself and holds one SMTP and one database connection of the Worker's 6 (ADR 0014, #11). Sending works on Workers Free: on a deployed Worker, one batch of 100 went out in one invocation in 226 seconds and 874 ms of CPU, so its host lookups and SMTP connections didn't meet Free's 50-subrequest limit (#11).

## Providers

- Mailquilt never sends an Organization's email itself, on the hosted service either. Its own account emails go through the System Mailer (ADR 0002).
- An Organization can have several Provider Connections, with one default for Campaigns and one for Transactional Messages, and an override per Campaign. Failover between them is P3 and opt-in.
- Cloudflare Email is labelled beta, because Cloudflare's docs describe it for transactional mail and haven't confirmed bulk sending.
- SES is called through `aws4fetch` on both targets, so one adapter runs on Workers and Node.
- Plain SMTP has no bounce handling beyond signed bounce addresses until bounce-mailbox polling in P2.
- An SMTP Provider Connection's encryption is `tls` (from the start), `starttls` or `none`. `starttls` refuses a server that doesn't offer STARTTLS rather than sending unencrypted (#9).
- Both the SMTP username and password are credentials: sealed, write-only, never returned. Some services, such as Postmark, use the same secret token for both (#9).
- A test email goes to any address the member types, through the connection's default sender, at most 10 every 10 minutes per person across Organizations. When the Provider refuses it, the API answers 502 `SendFailed` with the Provider's own words, so the member can fix the settings (#9).
- A Provider Connection can be edited and deleted. An edit that leaves credentials out keeps them; `null` removes them. Changing the host, port or encryption while keeping saved credentials is refused (`CredentialsRequired`), so a member can't send someone else's password to a server they control or unencrypted (#9).
- A DNS lookup that fails (timeout, server failure) is reported as `unreachable` with the resolver's reason; only a name with no address is `host-not-found` (#9).
- SMTP on Workers is the same Nodemailer adapter, over workerd's `node:net` and `node:tls`, which run on `connect()`. After the outbound guard checks the host, a Worker connects to it by name, because Cloudflare starts TLS only on a socket opened by name (ADR 0010); TLS from the start opens a TLS socket by name, since Nodemailer's own fails there. Cloudflare checks the certificate against that name. Workers can't trust extra certificates and block port 25, and a certificate the name doesn't match fails as `unreachable` with Cloudflare's own words ("proxy request failed", "Connection closed unexpectedly") rather than `tls` (#11).

## The install

- First-run setup makes the instance admin once, in the same transaction as the `instance` row, and never opens again. Whoever reaches a fresh install first becomes its instance admin; there is no setup token (ADR 0011, #7).
- The instance admin's email is marked verified at setup, because a fresh install has no System Mailer yet (ADR 0011, #7).
- Sign-up is invite-only by default, and refused before setup too, with 403 `SIGN_UP_CLOSED`. Until invitations (#34), invite-only means nobody can sign up (#7).
- The System Mailer sends through SMTP, with the same adapter and outbound guard as Provider Connections. Its saved credentials are sealed and write-only, and only go to the server they were entered for, as a Provider Connection's do (#7).
- `SYSTEM_MAILER_*` environment variables win over the System Mailer saved on the settings page, which then can't be changed (409 `SystemMailerFromEnvironment`). Some set but not all that are needed stops the app on Node; a Worker answers 500 to every request instead, saying why in its log (#7).
- An account email that can't be sent, including when the saved System Mailer can't be read, is logged with its subject and the failure's reason, never the address or the server's reply, which often quotes it. Sign-up still succeeds (#7).
- On Node the System Mailer answers at once and sends afterwards, so sign-up takes as long for a new address as for one with an account. On Workers it sends before answering, which is safe only while SMTP fails at once there, so the System Mailer still doesn't send on Workers, though Provider Connections do (#7, #11).
- Every field first-run setup takes accepts only what Better Auth signs in with, so setup can't make an instance admin who can never sign in. A new password is 8 to 128 characters (#7). An email address passes Better Auth's own check as well as the browser's, so `admin@localhost` is refused (#147).

## Data

- Postgres is the only database, including on Cloudflare (ADR 0001).
- On Cloudflare, Hyperdrive's query cache is off (`--caching-disabled`). With it on, reads are served up to a minute old: a Campaign that started sending still reads as a draft, and so would a session that was signed out (#11).
- IDs are a type prefix plus a UUIDv7 in the TypeID format, such as `org_01h455vb4pex5vsknk084sn02q`. They're part of the public API (ADR 0006).
- Every repository method for tenant data requires `CurrentOrganization` from the request context, which only `asMemberOf` provides after checking membership, `asQueuedFor` for the app's own queue messages, and the unsubscribe and preferences use cases for a signed link (ADR 0016). `@repo/core` exports it as a type only, so another package can provide it only by going around the type checker. There's no unscoped query path for tenant data, and Postgres row-level security isn't used (ADR 0007).
- The isolation suite fails when an endpoint for one Organization's data has no case from another Organization. An endpoint that also takes another resource's ID, such as a Campaign's List or Provider Connection, needs a second, hand-written case: a valid ID of a resource another Organization owns, such as its List, sent from inside your own Organization, so the test reaches the ownership check rather than failing on the ID's format. Nothing finds a missing one, so the pull request template asks (#43).
- Inside `db.transaction`, queries use `db`, never a `tx` argument. Drizzle runs the transaction on `SqlClient.withTransaction`, so it belongs to the fiber and `db` joins it, and a helper called inside gets it without being passed one (#43).
- The Organization a request acts in is named in its path, not stored on the session, so two tabs can work in two Organizations. The dashboard remembers each tab's choice (ADR 0007, #6).
- A Contact's email address is unique per Organization regardless of case, and kept as entered (#8).
- Email addresses are ASCII only, the same check as a browser's email field, so an address with non-ASCII characters in its name or domain is refused. Accepting them needs SMTPUTF8 support end to end (#43).
- Adding Contacts to a List subscribes only those with no Subscription to that List yet. An existing Subscription keeps its status, so a member can't subscribe again someone who unsubscribed, or skip a pending confirmation. The answer says how many were left as they were (#8).
- Adding Contacts to a List takes up to 50 at once (one page), and adds nobody if one of them doesn't exist (#8).
- Collections that grow with an Organization's audience are paged by ID, newest first, 50 per page, with a total and cursors both ways. Lists and Organizations are returned whole (ADR 0008, #8).
- Response schemas reuse input rules, so a stored value that fails a rule can't be returned. A change that tightens an input rule also migrates the stored values that would fail it, in the same pull request (#43).
- In the API, a field holding an ID is named for it (`listId`, `listIds`), in query parameters too, and a response gives a missing value as `null`, never as an absent key. The Contacts filter `list` and a sender's absent `name` are the exceptions left to fix before the first release (#158) (#43).
- Delivery events are partitioned by month through a hand-written migration, and dropped after 13 months by default once retention is built (#22). Campaign totals and Contact engagement summaries outlive them.
- Imports, recipient snapshots and event writes are set-based. There's never a query per Contact, except the two statements around each Campaign email: the claim, which also checks consent, since a batch can run for minutes and someone who unsubscribes or opts out partway through shouldn't get it (#12), and the outcome, recorded as soon as the Provider answers, so a batch cut off partway never sends anyone a second copy (#17).
- A rule over many rows at once, such as who receives a Campaign or which Contacts a List adds, is one SQL statement in the repository. `core` holds a use case's steps, not set logic (#43).
- Migrations are expand-then-contract. They run on boot behind an advisory lock in Docker, and in the deploy step on Cloudflare.
- Migrations run in one transaction, so `CREATE INDEX CONCURRENTLY` isn't available: an index on a large table, such as delivery events, holds up writes to it while it builds, at boot on Docker and in the deploy step on Cloudflare. That's accepted while tables are small; such a migration gets its own plan. Migrations don't set a `lock_timeout` yet (#158) (#43).
- A Campaign's recipients and delivery events have no TypeID: no endpoint names one, so they're keyed by the Campaign and Contact (recipients) or a sequence and the time (events) (#10).
- An Organization's data is deleted 30 days after a hosted plan is cancelled.

## Security

- Better Auth sits behind our own allow list of endpoints. `disabledPaths` is only a second layer, and plugins we don't use aren't installed.
- Better Auth's rate limiter uses our `RateLimiter` port in every environment. Its in-memory store is never used.
- Sign-in is limited to 20 tries an hour per account, from any IP. Anyone who knows an address can use up those tries and keep its owner, the instance admin included, from signing in for an hour. That's accepted, because the limit stops password guessing across many IPs; on hosted, Turnstile (#38) makes it costlier (#43).
- The client IP is read only from the configured header: `cf-connecting-ip` on Cloudflare, the proxy's header on Docker.
- Every outbound request to a user-chosen address goes through the outbound guard, and connects to the address it checked (ADR 0010), except SMTP on Workers, which connects by name after the check because Cloudflare starts TLS only on a socket opened by name (#11). It's always on for hosted; self-hosted installs allow private networks and loopback by default. Cloud metadata, link-local and reserved addresses are always refused (#9).
- Secrets at rest are sealed with AES-256-GCM under `ENCRYPTION_KEYS`, bound to their row; the app doesn't start without valid keys (ADR 0009, #9).
- On the hosted service, public pages are served from a domain that never receives cookies, and open and click tracking requires the Organization's own tracking domain.
- Redis isn't used. A Redis rate limiter is added only if several replicas or measured Postgres load need it.
- Self-hosted installs send no usage telemetry. The only call home allowed is an update check that can be turned off (#40).

## Building and testing

- The dashboard is a static SPA. Public pages are rendered on the server by the same deployed app.
- A dashboard dialog is Kumo's `LayerDialog` on desktop, centred over the dark scrim: the title and content on a card inside a frame, with Cancel at the frame's far left and the action at its far right. Phones keep the bottom sheet built on Base UI's Drawer, because `LayerDialog`'s own phone layout puts the desktop card inside its drawer. #70 had replaced `LayerDialog` with Kumo's one-card `Dialog`; the maintainer compared both and chose `LayerDialog` (2026-11-23).
- A dashboard request the API refuses with `SignInRequired` isn't retried. The query client checks the session again, and when it has ended, `SignedInOnly` sends the person to sign in. Pages and forms don't handle `SignInRequired` themselves, and whatever was typed into an open form is lost (#58).
- On Node, pg-boss is both the Queue and the Scheduler.
- Persistence is never tested with in-memory fakes (see `testing.md`).
- A failure a caller handles is a typed error: `Schema.TaggedError` in `domain` when the API returns it, `Data.TaggedError` in `core` otherwise. Anything else, such as an unexpected SQL error, becomes a defect through `Effect.orDie`, not `catchTag(…, Effect.die)` or a fallback value that hides it (#43).
- An API error's HTTP status is set once, in `packages/contract/src/errors.ts`, and every endpoint that returns it takes it from there, so one error has one status everywhere (#43).
- `@cloudflare/vitest-pool-workers` isn't used while it needs Vitest 4 and `@effect/vitest` needs Vitest 5. The Cloudflare runtime is covered by the smoke test on `wrangler dev`.
- Every dependency is pinned exactly in one pnpm catalog, with a 7-day `minimumReleaseAge`. `drizzle-orm` and `drizzle-kit` are excluded, because the Effect integration exists only in their newest release candidates.
- A package pnpm installs only as another's peer, such as `redis` for `@effect/platform-node`, sits outside the catalog. One that ships in the Docker image is added to the catalog, so its version is chosen on purpose (#158) (#43).
- CI installs with `--frozen-lockfile` in every job, so tests never meet a dependency version the repo hasn't taken on purpose.
- Dependencies are updated by hand, with no Renovate or Dependabot update PRs, so no third-party app gets write access to the repo. Dependabot alerts and `pnpm audit` in CI flag vulnerable versions. At each checkpoint in `ROADMAP.md`, run `pnpm outdated -r` and update what's worth it. This replaces the Renovate setup from #3.

## Product

- No core feature is gated by hosted plan. `ee/` holds only white-label, SSO, the full audit log, advanced roles and the approval workflow, from P4.
- Creator monetization (paid subscriptions, referrals, ad network) isn't planned.
